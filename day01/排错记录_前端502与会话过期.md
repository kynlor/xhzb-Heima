# 排错记录：前端 502 / 验证码不显示 / "会话过期"

> 环境：Docker Compose 部署的 RuoYi 架构项目（Vue3 前端 + Spring Boot 后端）
> 宿主机：192.168.40.40　访问入口：http://192.168.40.40/
> 现象：打开页面验证码加载不出来，弹"会话过期"，偶发 502 Bad Gateway

---

## 0. 一句话结论（先看这个）

本次其实是**两个不同层面的问题叠在一起**：

| 现象 | 层面 | 根因 |
|---|---|---|
| 偶发 **502 Bad Gateway** | 网关层（nginx 连不上后端） | 后端 Spring Boot 启动慢/重启瞬间，nginx 连不上 upstream |
| 验证码不出 + **"会话过期"**（持续） | 应用层（连上了但路径错） | nginx 转发时**没削掉 `/prod-api` 前缀**，后端 `context-path` 是 `/`，路径对不上，Spring Security 返回 `code:401`，RuoYi 前端把 401 当成登录态失效 |

**关键认知：502 ≠ 会话过期。** 502 是"根本没连上后端"，401/会话过期是"连上了、但后端拒绝了这个请求"。排错时要先分清是哪一层。

                        ┌─────────────────┴──────────────────┐

## 2. 排错过程（含每一步的命令与判断）

### Step 1 · 容器都活着吗？

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

结果：7 个容器全部 `Up`，mysql/redis/milvus 还带 `(healthy)`。
→ **结论：不是容器挂了。** 排除"服务没起来"这个最粗的原因，往下走。

### Step 2 · 后端到底启动成功没有？

```bash
docker logs xhzb-admin 2>&1 | grep -iE 'started|error|tomcat|9000'
```

关键日志：
```
Tomcat started on port 9000 (http) with context path '/'
Started XhzbApplication in 12.018 seconds
```

→ **两个重要信息**：
1. 后端启动成功，监听 9000。
2. **`context path '/'`** ← 这行是本案的题眼，先记下。

（日志里还有一堆 logstash `192.168.100.168:5044` 和华为 IoTDA AMQP `127.0.0.1:5671` 连不上的报错——那是**噪音**，跟登录无关，排错时要学会过滤掉，别被带偏。）

### Step 3 · 看 nginx 到底怎么转发的

```bash
cat /data/nginx/conf.d/default.conf
```

原始配置的关键行：
```nginx
location /prod-api/ {
    resolver 127.0.0.11 valid=10s;
    set $upstream_server xhzb-admin:9000;
    proxy_pass http://$upstream_server$request_uri;   # ← 问题在这
}
```

`$request_uri` = 客户端发来的**完整原始 URI**，即 `/prod-api/captchaImage`。
→ nginx 把 `/prod-api/captchaImage` 原样丢给后端。可后端 `context-path` 是 `/`，它只认 `/captchaImage`。**路径对不上。**（假设，待验证）

### Step 4 · 分层验证（最关键的一步：用 curl 把链路拆开测）

不要只在浏览器里点，要用命令行**逐段**打，才能定位断点在哪：

```bash
# ① 直连后端，带 /prod-api 前缀
curl -s http://127.0.0.1:9000/prod-api/captchaImage
# → {"msg":"请求访问：/prod-api/captchaImage，认证失败，无法访问系统资源","code":401}

# ② 直连后端，不带前缀（后端真正的路径）
curl -s http://127.0.0.1:9000/captchaImage
# → {"msg":"操作成功","img":"/9j/4AAQ..."}   ✅ 正常返回验证码

# ③ 经过 nginx
curl -s http://127.0.0.1/prod-api/captchaImage
# → {"...","code":401}   ❌ 和 ① 一样
```

**这三条 curl 直接锁定了根因：**
- ② 证明后端接口本身是好的，路径就是 `/captchaImage`。
- ① 证明只要路径带上 `/prod-api`，后端就返回 `code:401`。
- ③ 证明 nginx 转出去的路径确实带了 `/prod-api`（和 ① 结果一致）。

→ **实锤：nginx 没有削掉 `/prod-api` 前缀。**

### Step 5 · 为什么是"会话过期"而不是"404"？

后端 `@GetMapping("/captchaImage")`，但你请求 `/prod-api/captchaImage`：
- 这个路径后端没有对应 Controller；
- Spring Security 发现是"需要认证但没带 token"的未知路径 → 返回 RuoYi 的 `AjaxResult{code:401}`（注意 **HTTP 状态码其实是 200**，401 在响应体里）；
- RuoYi 前端拦截器看到 `code === 401` → 弹「会话过期，您可以继续留在该页面，或者重新登录」。

→ 所以你看到的"会话过期"是**假象**，真实原因是路径错了。这也是为什么很多人第一反应去查 token/Redis/登录逻辑，全跑偏了。

## 3. 修复

在 `location /prod-api/` 里加一行 `rewrite`，转发前把 `/prod-api` 前缀削掉；顺便给前端 `location /` 加 `try_files`（Vue history 路由刷新不 404）：

```nginx
location /prod-api/ {
    resolver 127.0.0.11 valid=10s;
    set $upstream_server xhzb-admin:9000;
    rewrite ^/prod-api/(.*)$ /$1 break;      # ★ 新增：削掉 /prod-api 前缀
    proxy_pass http://$upstream_server;       # 注意：去掉了 $request_uri
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 300s;
    proxy_send_timeout 300s;
    proxy_read_timeout 300s;
}

location / {
    root   /usr/share/nginx/html;
    index  index.html;
    try_files $uri $uri/ /index.html;         # ★ 新增：Vue history 模式
}
```

**应用流程（改配置的标准动作，别跳步）：**

```bash
# 1. 备份原配置（改线上配置前必备份！）
cp -a /data/nginx/conf.d/default.conf /data/nginx/conf.d/default.conf.bak.$(date +%s)

# 2. 写入新配置（略）

# 3. 语法校验——不校验直接 reload，配置写错会导致 nginx 起不来
docker exec xhzb-ui nginx -t

# 4. 平滑重载（不断连接）
docker exec xhzb-ui nginx -s reload

# 5. 立刻验证
curl -s http://192.168.40.40/prod-api/captchaImage | head -c 100
# → {"msg":"操作成功","img":"/9j/4AAQ..."}   ✅
```

> 小插曲：`nginx -s reload` 后**紧接着**在同一条命令里 curl，可能还打到旧 worker 上，看到旧的 401——这是 reload 的瞬时竞态，隔一下再测就对了。别被这个假象骗到以为没改成功。

## 4. 深入：502 Bad Gateway 专题

### 4.1 502 是什么

`502 Bad Gateway` = **nginx 作为网关，向后端（upstream）要响应，但后端没给它一个有效响应**。注意：这是 **nginx 自己生成的错误页**，请求根本没到达（或没正常到达）后端应用。

和它容易混的几个：

| 状态码 | 含义 | 谁的锅 |
|---|---|---|
| **502** Bad Gateway | 连上了后端但拿到无效响应，或压根连不上（连接被拒/超时） | 后端挂了/没起/IP 不对 |
| **503** Service Unavailable | 服务不可用（过载、维护） | 后端 |
| **504** Gateway Timeout | 连上了后端，但后端**响应太慢**超过 nginx 等待时间 | 后端处理慢 |
| **499** | 客户端主动断开（nginx 特有） | 前端/用户 |
| **401/403**（在响应体里） | 连上了、后端也处理了，但**拒绝**了请求 | 应用逻辑（本案的"会话过期"） |

**本案区分**：
- 502 = 网关层，"我（nginx）找不到/连不上后端" → 后端启动慢或 IP 变了。
- 会话过期(401) = 应用层，"后端收到了，但说你没权限" → 路径没削前缀。

### 4.2 Docker 环境里 502 的常见成因

1. **后端还没起来**：Spring Boot 启动要十几秒，nginx 已经就绪并收到请求，转发时后端端口还没监听 → 连接被拒 → 502。（本案的偶发 502 最可能就是这个。）
2. **后端容器重启，IP 变了**：Docker 每次重建容器可能分配新 IP。如果 nginx 里把后端地址**写死成主机名且用了静态解析**，nginx 只在启动/reload 时解析一次 DNS 并**缓存旧 IP**，之后一直连旧 IP → 502。
3. **upstream 名字拼错 / 不在同一网络**：nginx 解析不到主机名。
4. **后端进程崩了但容器还在**（假活）：端口没人监听。
5. **SELinux 的 `httpd_can_network_connect` 关闭**：nginx 被禁止发起对外网络连接（RHEL/CentOS 常见坑）。

### 4.3 为什么当前配置能"自愈"IP 漂移

```nginx
resolver 127.0.0.11 valid=10s;         # 127.0.0.11 是 Docker 内置 DNS
set $upstream_server xhzb-admin:9000;  # 用【变量】存后端地址
proxy_pass http://$upstream_server;    # proxy_pass 里用了变量
```

nginx 有个规则：**只有当 `proxy_pass` 里出现变量时，才会用 `resolver` 在运行时动态解析 DNS**（并按 `valid=10s` 定期刷新）。这样后端容器重启换了 IP，nginx 最多 10 秒后就能解析到新 IP，**不用手动 reload**。

如果图省事写成静态的 `proxy_pass http://xhzb-admin:9000/;`（不带变量），nginx 会把 IP 缓存到下次 reload 为止 → 后端重启就 502。这就是"变量 + resolver"方案的价值。

### 4.4 进一步减少启动期 502（可选加固）

在 `docker-compose.yml` 里让前端**等后端真正健康**再启动：

```yaml
services:
  xhzb-admin:
    # ...
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:9000/captchaImage"]
      interval: 10s
      timeout: 5s
      retries: 12
      start_period: 40s      # 给 Spring Boot 留足启动时间

  xhzb-ui:
    # ...
    depends_on:
      xhzb-admin:
        condition: service_healthy   # 不是 service_started，而是等健康
```

> 注意：`depends_on` 默认只等"容器启动"，不等"应用就绪"。要等应用真正能服务，必须配 `healthcheck` + `condition: service_healthy`。

## 5. 可迁移的排错方法论（这才是重点）

1. **先建地图，再看现场**：搞清楚请求从浏览器到后端经过哪些环节（nginx → 应用 → DB/缓存）。
2. **自顶向下 or 自底向上分层定位**：本案用的是"分层 curl"——直连后端测一次、经过 nginx 测一次，一对比就知道断在哪一段。这是网关类问题最有效的手段。
3. **区分"网关层"和"应用层"**：502/504 是网关连不上/等超时；响应体里的 401/500 是应用处理了但出问题。别把两者混为一谈。
4. **别被表象带跑**：前端弹"会话过期"，不代表问题在登录/token/Redis。要顺着"前端为什么弹这个"倒推到"后端返回了什么 code"，再倒推到"后端为什么返回这个 code"。
5. **过滤噪音日志**：logstash、AMQP 连不上的报错和主流程无关，排错时先 grep 关键字（started/error/端口号）聚焦。
6. **改线上配置的纪律**：备份 → 改 → `nginx -t` 校验 → reload → curl 验证。一步都不能省。
7. **警惕瞬时竞态**：reload/重启后紧接着测，可能拿到旧结果，隔一两秒再确认。

## 6. 踩坑记录（真实遇到，附赠）

**Git Bash 的路径转换坑**：在 Windows Git Bash 里给脚本传参 `/data/nginx/conf.d/default.conf`，Git Bash（MSYS）会自作主张把它转成 Windows 路径 `D:/Tools/Git/data/nginx/conf.d/default.conf`，导致远程命令拿到错路径。

解决：执行命令前加环境变量禁用转换：
```bash
MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*' python your_script.py "/data/..."
```
或把远程路径**写死在脚本内部**（不经过 shell argv），就不会被转换。

## 8. nginx `proxy_pass` 路径规则小抄（本案核心知识）

| 写法 | 后端收到的路径 | 说明 |
|---|---|---|
| `proxy_pass http://host;`（无 URI、无 rewrite） | `/prod-api/captchaImage` | 原样透传请求 URI |
| `proxy_pass http://host$request_uri;` | `/prod-api/captchaImage` | 显式拼接完整原始 URI（本案原始 bug） |
| `proxy_pass http://host/;`（结尾带 `/`，**静态主机名**） | `/captchaImage` | 用 `/` 替换掉 location 前缀 `/prod-api/` |
| `rewrite ^/prod-api/(.*)$ /$1 break;` + `proxy_pass http://$var;` | `/captchaImage` | 先改写 URI 再透传（本案修复，兼容变量+resolver） |

**记忆要点**：
- `proxy_pass` 里的**地址（ip:port）只决定连哪台机**；**发给后端的路径**由"是否带 URI 部分 + 是否有 rewrite"决定，两者是分开的。
- **想用变量 + resolver 动态解析 DNS，就必须用 rewrite 削前缀**，不能用"结尾斜杠替换"（斜杠替换对变量不生效）。
- 结尾斜杠 `/` 的静态写法更简单，但后端重启换 IP 后会 502，需手动 reload。
