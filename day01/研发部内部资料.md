## 1. 研发中心组织架构与岗位职责

### 1.1 组织架构
```
研发VP / CTO
 ├─ 产品组（产品经理、UI/UX）
 ├─ 前端组（Web/移动端）
 ├─ 后端组（业务服务、中间件、基础架构）
 ├─ 测试组（功能、自动化、性能）
 ├─ 运维/SRE组（CI/CD、监控、稳定性）

```

### 1.2 关键岗位职责
| 岗位 | 核心职责 |
|---|---|
| 产品经理 | 需求分析、PRD、排期、验收 |
| 开发工程师 | 编码、自测、单元测试、技术方案 |
| 测试工程师 | 测试用例、功能/回归测试、缺陷跟踪 |
| SRE/运维 | 发布、监控、告警、故障处置 |
| 技术负责人 | 架构设计、技术选型、CR把关、风险把控 |

## 2. 研发流程规范（需求→上线）

### 2.1 标准开发流程
```
需求评审 → 技术方案设计 → 排期拆分 → 开发 → 自测
   → Code Review → 提测 → 测试 → 验收 → 预发验证 → 上线 → 复盘
```

### 2.2 各环节准入准出
- **需求评审准入**：PRD 完整、流程图清晰、边界明确
- **开发准入**：技术方案评审通过、任务拆分到人
- **提测准入**：自测通过、接口文档齐全、冒烟用例通过
- **上线准出**：测试通过、无遗留严重缺陷、回滚方案就绪

## 3. 代码管理规范

### 3.1 命名规范
- 变量/函数：小驼峰 `userName`
- 类/组件：大驼峰 `OrderService`
- 常量：全大写下划线 `MAX_RETRY_COUNT`
- 包/目录：小写连字符 `user-center`

### 3.2 注释规范
- 公共方法必须有注释（功能、参数、返回值、异常）
- 复杂业务逻辑注释"为什么这么做"，而非"做了什么"
- 禁止保留大段注释掉的死代码

### 3.3 编码通用要求
- 单一职责、函数短小、避免深层嵌套
- 禁止硬编码（配置项走配置中心）
- 关键操作打日志（入参、出参、耗时、异常）
- 异常必须捕获处理，禁止吞异常

## 4. 分支与版本管理

### 4.1 分支模型（Git Flow 简化版）
| 分支 | 用途 |
|---|---|
| `main/master` | 生产环境代码，受保护 |
| `develop` | 集成分支 |
| `feature/xxx` | 新功能开发 |
| `release/x.x.x` | 发布准备 |
| `hotfix/xxx` | 线上紧急修复 |

### 4.2 提交信息规范（Conventional Commits）
```
feat: 新增订单导出功能
fix: 修复登录态过期问题
refactor: 重构支付回调逻辑
docs: 更新接口文档
chore: 升级依赖版本
```

### 4.3 版本号规则
- 格式：`主版本.次版本.修订号`（如 2.3.1）
- 主版本：不兼容的大改动
- 次版本：向下兼容的新功能
- 修订号：向下兼容的问题修复

## 5. 代码评审（Code Review）制度

### 5.1 原则
- 所有合并到主干的代码**必须经过 CR**
- 作者自评 + 至少 1 名同事评审
- 评审关注：正确性、可读性、安全性、性能

### 5.2 评审流程
1. 开发者提交 MR/PR
2. 自评：自测说明、影响范围、测试点
3. 评审者按清单检查（功能、边界、异常、安全）
4. 修改后复审，通过后方可合并

### 5.3 严重问题清单（一票否决）
- 空指针、越界、资源未释放
- SQL 注入、XSS、硬编码密钥
- 无错误处理、无日志
- 破坏已有功能

## 6. 测试与质量保障

### 6.1 测试分层
| 层级 | 内容 | 责任方 |
|---|---|---|
| 单元测试 | 函数/类级逻辑 | 开发 |
| 接口测试 | 服务间调用 | 开发/测试 |
| 功能测试 | 业务场景 | 测试 |
| 回归测试 | 新版本影响面 | 测试 |
| 性能测试 | 压测、容量 | 测试/SRE |

### 6.2 缺陷管理
- 缺陷分级：致命/严重/一般/建议
- 致命、严重缺陷未修复不得上线
- 缺陷全流程跟踪：新建→修复→验证→关闭

## 7. 发布与部署规范

### 7.1 发布原则
- 发布窗口固定（如工作日上午，避开周末/大促）
- 小步快跑，灰度发布优先
- 每次发布必须有**回滚方案**

### 7.2 发布流程
1. 发布申请（版本、内容、影响面）
2. 预发环境验证
3. 灰度发布（先小流量）
4. 全量发布
5. 观察期监控
6. 发布完成确认

### 7.3 回滚
- 出现严重问题立即回滚至上一稳定版本
- 回滚优先于排查，先恢复再定位

## 8. 线上运维与故障应急

### 8.1 监控告警
- 核心指标：CPU、内存、接口耗时、错误率、业务量
- 告警分级：P0（全挂）/P1（核心受损）/P2（局部）/P3（提示）

### 8.2 故障响应
- P0：15 分钟内响应，全员介入
- 故障处置：止损 → 恢复 → 定位 → 复盘
- 事后 48 小时内输出故障复盘报告

### 8.3 复盘原则
- 对事不对人，找系统根因而非追责个人
- 输出改进项，明确责任人与完成时间

## 9. 技术文档与知识库

### 9.1 文档要求
- 接口文档（OpenAPI/Swagger）与代码同步更新
- 架构图、部署图、流程图及时维护
- 新人入职文档（环境搭建、项目说明）

### 9.2 知识库
- 沉淀：踩坑记录、技术选型、最佳实践
- 定期整理，避免重复造轮子

## 10. 信息安全与保密

### 10.1 保密红线
- 严禁泄露源码、客户数据、接口密钥
- 密钥、密码走配置中心/密钥管理服务，禁止硬编码进代码
- 生产数据严禁带出、严禁用于本地测试（用脱敏数据）

### 10.2 权限管理
- 最小权限原则
- 离职/调岗及时回收仓库与线上权限
- 定期审计访问权限

---

## 11. 研发效能与绩效考核

### 11.1 考核维度
- 交付质量（缺陷率、线上事故）
- 交付效率（按期完成率）
- 技术沉淀（文档、复用、改进）
- 协作（CR、跨组配合）

### 11.2 反对形式主义
- 不以代码行数论英雄
- 不唯加班时长
- 鼓励工程改进、自动化、提效工具
